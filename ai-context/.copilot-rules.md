# Copilot Rules — Hotel Management System

These rules apply whenever GitHub Copilot (or any AI assistant) generates, modifies, or reviews code in this project.

---

## Identity

- Project name: **Hotel Management System (HMS)**
- Status: **Mostly completed — production-ready**
- Goal: Fix bugs, improve reliability, maintain stability

---

## Primary Rules

### RULE 1 — Understand Before Changing
Before generating any code change:
1. Read the relevant file(s) in full
2. Identify what function/component you are modifying
3. Search for all usages of that function/component
4. Understand how the change affects the full flow (UI → API → DB → Socket)

### RULE 2 — Never Break Existing Behavior
- Wrap logic changes in `if` conditions so the old path still works
- Prefer adding new code over modifying existing code
- If refactoring is needed, do it in small, isolated steps

### RULE 3 — No New Features Without Explicit Instruction
- Do not add new functionality unless the user explicitly asks
- Do not add new routes, models, pages, or components speculatively
- Do not "improve" working code by restructuring it

### RULE 4 — Preserve API Contracts
- Do NOT rename fields in API request or response objects
- Do NOT change route paths
- Do NOT change the shape of data returned by services
- The mobile app and dashboard depend on these exact shapes

### RULE 5 — Preserve Socket Event Names
These event names are used across backend, mobile app, and dashboard:
```
order:created       order:updated       order:updateStatus
table:updated       table:updateStatus
billing:request     bill:updated
kitchen:alert
menu:updated        category:updated
join:room           ping / pong
```
Do NOT rename any of these without updating all three codebases.

### RULE 6 — Multi-Tenancy is Mandatory
Every query to a shared table must include `restaurantId` in the WHERE clause.
```typescript
// ✅ Correct
await prisma.order.findMany({ where: { restaurantId, status: 'pending' } });

// ❌ Wrong
await prisma.order.findMany({ where: { status: 'pending' } });
```

### RULE 7 — Use Defensive Programming
```typescript
// ✅ Always check for null
const table = order?.table;
const label = table?.tableNumber ?? 'Unknown';

// ❌ Never assume
const label = order.table.tableNumber;
```

### RULE 8 — Follow the Layer Architecture
```
Route file     → define paths + middleware only
Controller     → parse request + call service + send response
Service        → business logic + Prisma queries + socket emits
```
Do not put Prisma queries in controllers.  
Do not put HTTP response logic in services.

### RULE 9 — Emit Socket Events After DB Writes
When a service modifies order/table/bill state, always emit the corresponding socket event:
```typescript
// After updating order
emitOrderUpdate(restaurantId, updatedOrder);

// After updating table
emitTableStatusUpdate(restaurantId, updatedTable);

// After generating bill
emitBillUpdate(restaurantId, bill);
```

### RULE 10 — Standardized Responses
Always use the helper utilities:
```typescript
import { sendSuccess, sendError } from '../utils/response.util';

// Success
return sendSuccess(res, data, 'Message here', 200);

// Error
return sendError(res, 'Error message', 400);
```

## Language-Specific Rules

### TypeScript (Backend)
- Use strict types — avoid `any`
- Define Zod schemas for all new request bodies in `validators/`
- Export singleton services — do not instantiate in controllers

### TypeScript / React Native (Mobile App)
- All API calls must go through service classes in `src/services/`
- State mutations must go through Zustand store actions
- Use `expo-router` for navigation — `router.push()`, `router.replace()`
- Do not call `SocketService` methods directly in components — use `AuthProvider`

### JavaScript / React (Dashboard)
- All API calls must go through service functions in `src/services/`
- Use `useContext(AuthContext)` for auth state
- Use `useContext(NotificationContext)` for socket/notifications
- Do not create new socket connections — use the one in `NotificationContext`

## What NOT to Generate

❌ Do not generate new database models/tables without being asked  
❌ Do not generate new pages/screens without being asked  
❌ Do not generate migration files  
❌ Do not generate test files unless asked  
❌ Do not add new npm packages without justification  
❌ Do not create global state where local state is sufficient  
❌ Do not use `console.log` for sensitive data (tokens, passwords)  
❌ Do not hardcode IPs, URLs, secrets, or credentials  

---

## Safe Change Checklist

Before submitting any change, verify:
- [ ] Existing tests/flows still work with this change
- [ ] No API response shape was changed
- [ ] No socket event names were changed
- [ ] All DB queries include `restaurantId`
- [ ] Null checks are present for all potentially undefined values
- [ ] Socket events are still emitted after state-changing operations
- [ ] No new dependencies were added unnecessarily
- [ ] The change does not affect the auth token flow
